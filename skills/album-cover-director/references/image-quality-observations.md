# Observe image quality without inventing certainty

Evidence reviewed: **2026-11-16**. Use this reference when an output looks weak,
several concepts converge, or a refinement loses its selected identity. These
are diagnostic questions within the existing workflow, not a new score, mode,
mandatory experiment, or generation allowance.

## Follow the evidence through the run

Distinguish supplied musical evidence, the intended direction, the assembled
request, and the observed image. A recent host incident describes a downstream
prompt contradicting project requirements; it does not establish an image-model
rendering defect ([reported incident](https://community.openai.com/t/gpt-6-claims-it-checked-project-sources-then-tells-the-image-model-to-do-the-opposite/1415830)).

Before attributing a failure to the image model, inspect the exact prompt sent
and the reference roles. Check contradictory line counts, stale title variants,
scene instructions inherited from another candidate, and an unintended edit
parent. Keep explicit user-wide constraints. Save the sent prompt using the
existing ledger's `prompt_file`; a path to an earlier plan is not that evidence.
`prompt-preflight.py` validates the contract, not the assembled prose or pixels.

Record only exposed and reported model/settings information. ImageGen is the
host's tool surface; its name and a conversational thinking setting do not
confirm a particular image model, quality, or complexity. Follow
`runtime-adapters.md`. A natural-language request is not proof of an API value.

## Replace vague quality judgments with observations

Use the relevant rows during the existing inspection. Describe what happened,
where, and at which viewing size; keep aesthetic preference explicit.

| Concern | Observe | Change only what addresses it |
| --- | --- | --- |
| Weak musical identity | Link the visible action or relation to supplied evidence; label title-only readings as hypotheses. | Revise the interpretation or its visual operation; do not invent lyrics or conflict. |
| Twelve similar ideas | Compare actual silhouette, title hierarchy, figure role, viewpoint and negative space without labels. | Rework the weaker duplicate's organizing relation, not merely its palette or material. |
| Correct words, weak cover | Inspect exact glyphs separately from the title's structural role and square-scale identity. | Repair the failed relationship while protecting the complete title and reading route. |
| Failed optical idea | Check the declared alignment, second reading, reflection or join at its intended thumbnail size. | Repair that relation; a beautiful ordinary scene does not demonstrate the illusion. |
| Reference contamination | Inspect which source supplied face, setting, palette, camera and light. | Retain essential identity; explicitly permit scene-dependent changes where needed. |
| Unclear edit target | Identify the actual visible target and surrounding invariants. | Use a unique feature or supported region control, then inspect the whole output. |
| Polish loses the idea | Compare the new image to the selected source, not to memory. | Restore selected flatness, spacing, contact, depth or optical relation before adding detail. |
| Unwanted texture or alpha | Locate the artifact at full size and at display size; inspect the actual file. | Address the observed defect without claiming a hidden cause or universal model bias. |

Use existing viewing conditions: 56 px for the primary signal, 128/256 px for
reading and structure, full size for glyphs and artifacts, plus grayscale and
blur where applicable. Judge an illusion at its declared condition; do not
require every second reading at every scale. A prompt name, label or checksum
cannot prove that a visual relationship worked.

Correct text can coexist with incorrect camera or object relationships in
small recent tests ([camera comparison](https://www.reddit.com/r/generativeAI/comments/1xpu988/gpt_image_26_flare_vs_sunburst_same_prompts_28/),
[object/edit comparison](https://www.eachlabs.ai/blog/gpt-image-2-6-tested-on-eachlabs)).
Treat these as author reports, not model-wide failure rates or a reason to
avoid ambitious native lettering.

## Preserve deliberately and learn from authorized work

For an edit, name both what must remain and what may change. Identity and title
geometry may be invariant while light adapts to a new location. If light is
itself part of the chosen concept, preserve it. Do not impose one project's
reference-count cap or fixed-expression policy on every artist.

Higher rendering quality is not a different idea, and higher complexity can
introduce changes. Use those controls only when exposed and justified by the
specific defect ([current model guidance](https://developers.openai.com/api/docs/guides/image-generation#gpt-image-26)).
Do not automatically rerender an approved preview on another model and call it
an improvement. Keep its source, selection reason and production invariants.

Reuse `diversity_review`, `run-ledger.jsonl` and `cover-report.md` for the
observation, rejected candidate, next change and outcome. Report preference
separately from requirement failure. Keep private lyrics, images and actual
prompts artist-local under the existing storage rules.

Use the outputs of normal authorized work. This reference does not require a
pilot batch, paired image experiment, extra rerolls, or another user approval
step. Preserve the existing budgets and adopted-source rule. If an intended
relationship has not been inspected in an actual image, record it as unverified.

For maintainers, the repository's dated research report and source ledger
record the evidence window, access limits and unresolved questions. Recheck
relevant primary sources when a model/host changes or a reported issue gains a
resolution; do not silently turn an older-model result into current guidance.
